# Connect v0.9.1 USB gamepad design — proposed

Status: approved and implemented on 2026-11-03. See the implementation progress report for validation results. The user will perform Linux/controller testing on their separate Linux machine.

## Intent and scope

Fix incorrect controller buttons on Linux viewers and let users detect, test, and rebind their USB controllers in Settings. The reported failures include physical Xbox A arriving as X and LB arriving as LT. Preserve working Windows controller support and produce Windows and Linux builds of v0.9.1.

The supplied source is v0.9.0, protocol 8. It is a source archive without `.git` or `.github`; review and implementation must use this supplied baseline unless another checkout is explicitly selected. The public repository page reviewed during planning described v0.7.0, so it must not silently replace the supplied baseline.

Linux remains a viewer; Windows remains a host and viewer. Bluetooth, Linux hosting, rumble, macros, keyboard/mouse bindings, and streaming performance changes are outside this release. Existing backend handling is not a promise of Bluetooth support. Stick movement must remain correct and visible in the tester; a new stick calibration/editor is outside this button-focused release.

## Current behavior and evidence

- `app/src/gui/gamepad.rs`: a session-owned thread creates `Gilrs`, reads named buttons/axes, and sends changed full `GamepadState` reports. Its hardcoded mapping has no user override. Native source codes from events are not used by Connect. There are no tests of this capture/mapping layer.
- `app/src/gui/mod.rs`: creates that reader only after session acceptance. Settings cannot currently discover or test controllers before connecting.
- `app/src/gui/pages.rs`: Settings has Viewing and Windows-only Sharing cards, but no local-controller card. Sharing's driver installer is for host virtual controllers, not Linux physical-controller detection.
- `app/src/gui/settings.rs`: persists settings via serde/RON with defaults for older configurations.
- `crates/proto/src/input.rs`: already supports four slots, 15 digital Xbox buttons, separate 0–255 LT/RT, and four signed stick axes. Reliable, ordered input carries complete reports.
- `crates/host/src/input/windows.rs`: copies these report fields to ViGEm's Xbox 360 report. Host permission checks and release-on-revocation already exist.
- `gilrs` 0.11.2 is already installed and locked. It provides hotplug events, controller UUID/name/VID/PID, native `Code`, and cached state by native code, including controls without a known logical name. Events/state are normalized by gilrs; they are not unmodified Linux evdev records.
- Existing protocol input tests passed during planning: round-trip framing, device permissions, and event validation (3 tests). This does not test a physical Linux controller.

The symptoms are consistent with an incorrect device/driver/database layout, but the failing controller model and Linux hardware trace are not yet available. Do not hardcode a global Linux A/X or LB/LT swap: that would break other controllers. First identify whether the mismatch is in physical capture, logical mapping, report encoding, or host injection. In particular, gilrs calls bumpers `LeftTrigger`/`RightTrigger` and analog triggers `LeftTrigger2`/`RightTrigger2`; Connect's existing interpretation of those names is correct.

## Approaches considered

1. **Keep gilrs, add local detection and native-code-aware profiles — recommended.** Reuses both platform backends, transport, permissions, and host emulation. A small app-owned binding evaluator makes corrections independent of potentially wrong logical labels and persists them without changing the protocol.
2. **Use gilrs custom mappings exclusively.** Its `Mapping`/`set_mapping` APIs and SDL mapping strings are useful for device layout fixes, but require care with generated D-pad buttons, axis/button aliases, persistence, and partial mappings. A verified device-specific upstream mapping may fix the default, but by itself does not supply the requested settings, testing, and safe editable profiles.
3. **Replace the backend with SDL or direct Linux evdev.** Adds migration, packaging, and behavior risk across Windows and Linux without evidence that gilrs cannot deliver these USB events. Reconsider only if the reproduction proves a backend limitation.

This is a recommendation, not a user-approved choice. No dependency upgrade or new controller library is planned.

## Proposed behavior

### Settings → Gamepads (available on both platforms)

- Discover USB controllers before a session, and update the list on plug/unplug. Show the OS name, optional VID/PID, current automatic/custom profile, and forwarding slot when connected. Show backend initialization failures explicitly, separately from “No controller detected.”
- Select a controller to see a live input tester: physical source identifiers and current logical labels in an expandable diagnostic area, and the resulting Xbox buttons, triggers, and sticks in the normal view. Normal users see Xbox names such as LB and LT, not gilrs terminology.
- For each Xbox button and LT/RT: select **Rebind**, then press the desired physical control. Include **Unbind**, **Apply**, **Cancel**, and **Reset to automatic**. A guided “press A, B, X, Y…” pass can use the same capture mechanism; it is not a second mapping engine.
- Rebinding is controller-local and staged. Wait for controls to be released before capturing a fresh actuation; stick drift, an already-held button, button-repeat events, and other controllers cannot satisfy capture. LT/RT binding also records released/fully-pulled endpoints when the source is an axis.
- Reject ambiguous simultaneous actuations and show a retry message. A physical source/direction has one destination by default; a conflicting assignment is reported and must be moved or cleared explicitly before Apply. Opposite halves of a shared axis are distinct sources. No silent A+X or LB+LT duplication.
- Testing and rebinding remain local. Settings is currently hidden during a viewing session; v0.9.1 does not add an in-session settings overlay. Apply a profile before connecting, or disconnect to edit it.
- Users can switch between automatic mapping and their saved correction. Save profiles by platform plus controller UUID and available VID/PID, with a name fallback for devices lacking usable identity. Never persist runtime `GamepadId` or player slot. Identical models share a layout profile; distinguish their live instances in the UI.
- A profile is local to this viewer, not per host, and is restored after restart/replug. Windows and Linux native codes are never interchanged. If a profile is invalid or belongs to a different device, ignore that profile with a visible message without losing the user's unrelated settings.

### Runtime ownership

- Extend `gamepad.rs` from a session-owned forwarder to one App-owned controller worker. It owns the only gilrs instance, connected-device state, session attachment, and active slot assignments. No additional reader for the Settings page.
- Feed UI snapshots through latest-state storage with a small bounded recent-event history for rebinding. UI snapshots can coalesce; network button transitions cannot. Wake the GUI for controller activity only when the tester is visible.
- Keep input forwarding on the worker thread and event-driven, independent of video rendering and GUI refresh. The existing 50 ms `next_event_blocking` timeout is a control/idle timeout, not a mandatory delay on each input event. Retain its basic event-driven behavior; use a fixed control wake bound of at most 20 ms for detach/focus/stop handling, without a user-facing polling setting.
- Capture source identity and state from gilrs events/cache even if their logical label is `Unknown`. Preserve existing gilrs state updates and filters; do not invent an additional OS input backend or apply a second deadzone to already-filtered stick values.
- Automatic mode preserves existing named-input behavior. Custom mode resolves an explicit destination-to-source profile seeded from the automatic bindings, then applies the user's edits. Evaluate buttons from their pressed state, analog triggers from their value/range, and axis-backed digital inputs from their direction with hysteresis. Keep pressed and analog-value state separate so duplicate gilrs press/change notifications do not create artificial full-trigger spikes.
- Convert output once to the existing `GamepadState` and send every changed report in order, including brief press/release pairs. Analog LT/RT retain their range, not only digital on/off. Digital-to-trigger assignments intentionally produce 0 or 255. Stick values retain Xbox's up-positive Y orientation and signed range.
- Allocate slots only for a live session, keep each stable until unplugged, preserve the four-controller limit, and explain when extra controllers are not forwarded. Discovery/testing can list more than four devices.
- Neutralize/unplug as appropriate on focus loss, permission removal, device removal, session detach, worker failure, and app shutdown. On focus regain send the current complete state even if no new device event occurred. Ensure a previous worker/session cannot continue sending into a replacement session. Editing or resetting profiles cannot leave stale held state.

### Persistence and compatibility

Add a defaulted, versioned `gamepad_profiles` section to existing Settings; no separate config location. Validate profile records separately so a bad record does not reset the account, trusted hosts, or viewing preferences. Keep capture candidates/drafts out of persisted settings until Apply.

Keep protocol version 8 and the current `InputEvent`/`GamepadState` wire representation. Test v0.9.1 viewer → v0.9.0 Windows host and v0.9.0 viewer → v0.9.1 Windows host; protocol compatibility also covers 0.8 peers in principle, but do not advertise extra version coverage without testing it.

## Release acceptance

1. On Linux over USB, the reported controller's A produces Xbox A only; X produces X only; LB/RB produce shoulders only, and LT/RT remain independent analog triggers. Verify every remaining button, D-pad diagonal, stick direction, and simultaneous combination in a Windows tester and at least one game.
2. Detect before connecting, hotplug, rebind, Apply/Cancel, unbind, reset, restart, and replug all work. A fast press/release is preserved.
3. Test one, two, and four controllers; no cross-controller binding capture, slot churn, or stuck state. A fifth controller gets a clear non-forwarded status.
4. Losing focus, revoking host permission, unplugging while held, disconnecting, and closing Connect all release remote state. Local testing cannot control the host.
5. Existing Windows USB mapping works unchanged in automatic mode. Old Settings load without losing preferences. No Bluetooth compatibility claim.
6. Both release artifacts build and launch: `connect.exe` and `connect-linux-x86_64`. Check Linux linked libraries against the existing glibc 2.39 baseline; publish their checksums in the updater's existing `SHA256SUMS.txt` format.
7. The worker sends events without waiting for a UI frame, and settings discovery does not add a growing event queue or continuous GUI redraw while idle. Compare input traces before/after on the same hardware; report actual results rather than claim an unmeasured latency improvement.

## Unresolved evidence

The exact USB controller model, Linux distribution/kernel, and native input codes are unknown. Capture them in the first implementation task. They are required for accepting the reported hardware fix, not for designing or unit-testing configurable mapping. This Windows environment currently has only the Windows MSVC Rust target installed; Linux and physical two-PC validation require an appropriate build/test environment.
